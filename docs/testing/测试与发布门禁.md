# 测试、证据与发布门禁

所有测试标准按规则R27～R30/R41/R42/R43。以下定义执行及证据组织，不降低原标准。

## 两个完全独立的结果

1. **文档包校验**：脚本检查格式、链接、元数据和清单一致性；报告位于本包`reports/`。
2. **产品验收**：真实代码/平台/数据库/对象存储/发行签名/Host/TB负载；证据位于实际项目`.delivery/`或受限CI。

第一类通过不自动让第二类通过。本包没有产品运行证据。

## G0～G4执行顺序

G0合同一致和反例；G1静态/类型/格式/安全检查；G2单元/属性/边界测试；G3真实PG/对象/IPC/协议集成和故障；G4目标OS、混合负载、恢复、安全审查和维护交接。具体原有定义以规则R40为准。新增工具需未授权、越权、超量、超时、重放和schema反例。

## 每份证据应包含

规则/测试ID、代码commit或完整工作树digest、合同digest、migration/依赖版本、环境/负载、命令argv、开始/结束、退出码、报告路径/hash、断言内容、覆盖与限制。合并或合同变化后重跑影响范围；旧pass不得自动满足新版本。

Mock只能隔离单元行为；不能以MockPG证明事务、以fake S3证明multipart、以合成截图证明真实接口。C1/C2不能用同一内容去重后几块数据或稀疏文件冒充。

## 交付追踪

维护 `需求/规则ID → 模块owner → 工作项 → 实现路径 → 测试 → 当前证据 → 用户文档 → release artifact`。缺任何链路都列为待办。文档更新也接受链接/样例校验；不因无代码改动就不审MCP权限描述。

## 不具备条件时

真实Windows/macOS runner、1TiB文本环境、生产证书、IdP或外部服务不可用时明确blocked/未测，继续无依赖开发，不关闭校验。scope变化、签名失败、数据丢失风险属于停止对应发布项的条件。

正式签收见[验收清单](../handoff/验收签收清单.md)，不能由模型替客户、安全和运维审批者签字。

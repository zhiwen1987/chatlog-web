# 日常运维手册

目标：保持可查询、可校验、可取回，并能在问题扩大前发现。产品SLO和容量门槛引用规则R16/R18/R20/R29/R38，以下为操作顺序。

## 每日观察

检查客户服务端live/ready区别、PG/对象空间水位、复制/WAL归档、最老未处理job、索引覆盖、媒体未验证/失败增长、设备presence与数据停滞分别统计、license最后可信续租与功能到期。发行方单独看签名器健康、未发布outbox、批次冲突和租约成功率。

以聚合指标找异常，再用受限ID日志定位；不将每个device/file作为无界指标label。心跳原包不永久追加日志，状态转换与异常才记录；不要让监控本身填满盘。

## 每周/定期

抽验备份可恢复、查即将到期证书/凭证、测试最小权限账号和应急流程；检查未完成multipart/孤儿对象的受控GC、索引和表增长、慢查询计划、角色及外发授权变更。删除GC先确认引用、上传session、保留和删除账本，不能按文件年龄直接删。

## 过载处理顺序

先保障Q0心跳/登录/取消和必要取回；对批量历史、全量hash、OCR/转码减并发或进入paused_resource；观察PG连接总量、锁、CPU、I/O和网络瓶颈。按租户和来源公平配额，不让一个TB账号长期饿死其他账号。

若磁盘危险，暂停新增扫描/接收并明确429/503与重试策略；保留已ACK资料和未ACK本地队列。不要以关闭完整性校验换吞吐，也不要在离线队列满时静默丢最老任务。

## 变更管理

配置、feature desired、依赖版本、索引、retention和许可策略都需版本、差异、批准者及回退计划；生产变更不能因“Agent自主”跳审批。发证和数据ACL分工，批次更改逐item可追踪。

## 告警处置完成的定义

当前故障止血、根因可解释、数据完整性核验、当前版本回归、告警阈值复核、后续任务有owner。不能只把告警阈值放宽就标解决。具体案例见[排错](日志与排错.md)与[恢复应急](备份恢复与应急.md)。
